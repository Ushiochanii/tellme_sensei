# TellMeSensei v0.8.1 — Context + Question Auto Watch

## 1. Document status

This document defines the implementation plan for TellMeSensei v0.8.1.

v0.8.1 extends the stable v0.8.0 Auto Watch feature with a dual-region workflow for questions that share a common passage, case description, table, diagram, or other context across multiple sub-questions.

The implementation target is intentionally narrow:

> Monitor one Context region and one Question region on the same display, combine them into one logical analysis input, and preserve all existing v0.8.0 Auto Watch guarantees such as stable-frame detection, Latest-Wins dispatching, cancellation, stale-result rejection, pause/resume, Analyze Now, Stop, DPI-aware capture, and lifecycle cleanup.

This is an incremental v0.8.x feature, not an Auto Watch rewrite.

---

## 2. Baseline

v0.8.0 is the required development baseline.

The current Auto Watch implementation already provides the following reusable building blocks:

- `app/auto_watch/detector.py`
  - lightweight grayscale change detection
  - baseline-vs-current novelty comparison
  - frame-to-frame stability comparison
- `app/auto_watch/stability.py`
  - consecutive stable-sample tracking
- `app/auto_watch/coordinator.py`
  - synchronous monitor state machine
  - `ARMING`, `WATCHING`, `CHANGING`, `PAUSED`, `STOPPED`
  - stable-frame generations
  - Analyze Now baseline acceptance
- `app/auto_watch/sampler.py`
  - DPI-aware single-screen capture
  - logical ROI to physical screenshot mapping
- `app/auto_watch/dispatcher.py`
  - one active analysis request
  - one latest pending request
  - Latest-Wins semantics
  - cancellation of obsolete analysis
  - generation/session guards
  - stale-result discard
- `app/ui/auto_watch_session.py`
  - session lifecycle
  - polling timer ownership
  - display configuration validation
  - monitor/analysis signal routing
  - fault handling and cleanup
- `app/ui/watch_overlay.py`
  - click-through ROI border outside the monitored pixels
- `app/ui/watch_mini_controller.py`
  - Pause / Resume / Analyze Now / Stop controls
- `app/ui/answer_window.py`
  - Auto Watch answer presentation
  - generation-aware updates
  - automatic placement outside the monitored ROI

v0.8.1 should extend these components where appropriate and add narrowly scoped new components only where the dual-region semantics actually require them.

## 3. Product problem

Many examination interfaces do not present every question as a self-contained block.

Typical examples:

```text
┌─────────────────────────────────────────┐
│ Context / Common Passage                │
│                                         │
│ Long passage, case description, table,  │
│ network diagram, chart, source text...  │
│                                         │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ Question                                │
│                                         │
│ Q3. Which statement is correct?         │
│ A. ...                                  │
│ B. ...                                  │
│ C. ...                                  │
│ D. ...                                  │
└─────────────────────────────────────────┘
```

The Context may remain unchanged for several questions while the Question region changes on every Next action.

Using one large v0.8.0 ROI works, but it has drawbacks:

- the common Context is repeatedly OCRed in Text mode;
- the user must include a large area even when only a small Question region changes;
- the semantic relationship between common Context and current Question is not explicit;
- Answer Window placement has less usable space when a single large bounding ROI is used;
- pages with separated Context and Question areas are awkward to monitor as one rectangle.

v0.8.1 addresses this by making Context and Question first-class regions.

## 4. User-facing feature definition

Auto Watch setup gains a Region Mode.

```text
Analysis Mode
● Text / OCR
○ Vision

Region Mode
● Single Region
○ Context + Question
```

`Single Region` preserves v0.8.0 behavior exactly.

`Context + Question` uses a guided selection flow:

```text
1. Select Context
2. Select Question
3. Start Auto Watch
```

The user can cancel or go back during setup without starting a session.

After both regions are selected, the setup view should visibly confirm both selections before the session starts.

Recommended setup presentation:

```text
Context
✓ Selected

Question
✓ Selected

[ Start Auto Watch ]
[ Back ]
```

The first stable Context + Question pair is analyzed automatically, matching v0.8.0 initial-stable behavior.

## 5. Scope

### 5.1 Included in v0.8.1

- one Context ROI;
- one Question ROI;
- both ROIs on one display;
- Text / OCR mode;
- Vision mode;
- one full-screen capture per polling tick;
- independent visual change detection for Context and Question;
- pair-level stable generation semantics;
- Context OCR caching in Text mode;
- structured Context + Question text passed to DeepSeek;
- in-memory Context + Question image composition for Vision mode;
- Latest-Wins behavior at the pair generation level;
- pair-aware Pause / Resume / Analyze Now / Stop;
- dual-region watch overlay;
- Answer Window placement avoiding both ROIs;
- regression compatibility with existing Single Region Auto Watch.

### 5.2 Explicitly out of scope

Do not add the following in v0.8.1:

- more than two monitored ROIs;
- Context and Question on different displays;
- multiple Context regions;
- automatic Context/Question region discovery;
- website-specific logic;
- DOM/browser extensions;
- saved ROI profiles;
- ROI persistence across restarts;
- Ignore Areas;
- sensitivity presets;
- adaptive polling;
- pHash or SSIM unless a real v0.8.1 failure demonstrates the current detector is insufficient;
- automatic Text vs Vision selection;
- iPad/mobile support;
- Local OCR version changes unrelated to this feature;
- Lite application changes.

The v0.8.0 detector is treated as stable unless v0.8.1 produces a concrete, reachable detector failure.

## 6. High-level architecture

The target architecture is:

```text
                    one QScreen capture
                           │
                ┌──────────┴──────────┐
                │                     │
          Context crop          Question crop
                │                     │
                ▼                     ▼
      Context Coordinator    Question Coordinator
                │                     │
       context revision       question revision
                └──────────┬──────────┘
                           ▼
                  Pair Coordinator
                           │
                  pair generation
                           │
                ┌──────────┴──────────┐
                │                     │
             Text/OCR               Vision
                │                     │
       Context OCR cache      Composite image
       + Question OCR               │
                │                     │
                └──────────┬──────────┘
                           ▼
              Existing Analysis Dispatcher
                           │
             Latest-Wins / cancellation
                           │
                           ▼
                      AnswerWindow
```

Key design principle:

> A Context + Question pair is the analysis unit. Context revision and Question revision are detector-level facts; pair generation is the only generation exposed to the analysis dispatcher.

## 7. Region model

Introduce a dual-region value object rather than overloading a single `WatchRegion` with optional fields.

Recommended model:

```python
class WatchRegionRole(Enum):
    CONTEXT = "context"
    QUESTION = "question"


@dataclass(frozen=True)
class ContextQuestionRegions:
    context: WatchRegion
    question: WatchRegion
    session_id: str
```

Validation requirements:

- Context and Question are both valid `WatchRegion` instances;
- neither ROI is empty;
- both belong to the same `QScreen`;
- both use the same session ID;
- both were created against the same screen geometry and device-pixel ratio snapshot;
- overlap is allowed if the user intentionally selects overlapping regions, but the UI should not encourage it.

No cross-screen pair support is needed.

## 8. Selection flow

The existing `CaptureOverlay` should remain the selection primitive.

Dual-region setup should reuse it sequentially:

```text
Select Context
    ↓
CaptureOverlay
    ↓
store Context WatchRegion
    ↓
Select Question
    ↓
CaptureOverlay
    ↓
store Question WatchRegion
```

The second selection must use the same screen as the Context selection.

If the user attempts to select the Question on another screen, reject the selection with a clear setup message and keep the already selected Context.

Suggested message:

```text
Context and Question must be on the same display.
Please select the Question region again.
```

A failed or cancelled Question selection should not silently discard the Context selection.

## 9. Capture strategy: one screenshot, two crops

Do not instantiate two independent `ScreenSampler` objects that each call `screen.grabWindow(0)` on every tick.

That would duplicate the most expensive screen operation without improving behavior.

Add a pair-aware sampler, for example:

```text
app/auto_watch/pair_sampler.py
```

Recommended API:

```python
@dataclass(frozen=True)
class ContextQuestionImages:
    context: QImage
    question: QImage


class ContextQuestionSampler:
    def sample(self) -> ContextQuestionImages:
        ...
```

Each tick must:

1. capture the screen once;
2. derive the physical Context crop;
3. derive the physical Question crop;
4. return detached `QImage` copies.

The logical-to-physical mapping must follow the same DPI-aware behavior as the existing `ScreenSampler`.

Expected steady-state cost:

```text
poll interval: 250 ms
full-screen captures per tick: 1
ROI crops per tick: 2
```

Do not write screenshots to disk.

## 10. Detector reuse

Each region should use the existing visual detector and stability rules.

Do not create a new image-comparison algorithm for dual-region mode.

Each region retains its own:

- baseline frame;
- previous frame;
- stability tracker;
- monitor state;
- region revision.

Initial detector configuration remains the v0.8.0 configuration unless later evidence requires a change:

```text
max side: 96 px
poll interval: 250 ms
pixel delta threshold: 15
novelty ratio: 0.06
stability ratio: 0.015
stable samples: 3
```

The pair layer consumes accepted stable-region events; it should not inspect raw pixels itself.

---

## 11. Region revisions and pair generation

Maintain three independent counters:

```text
context_revision
question_revision
pair_generation
```

Example:

```text
Context revision: 2
Question revision: 7
Pair generation: 10
```

Only `pair_generation` is passed to the analysis dispatcher.

This is important because Context and Question do not change at the same rate.

Do not reuse the Question coordinator generation as the AI generation.

---

## 12. Pair Coordinator

Add a small orchestration layer, for example:

```text
app/auto_watch/pair_coordinator.py
```

Its responsibility is to combine two stable-region state machines into one logical pair stream.

It should own or receive:

- Context coordinator;
- Question coordinator;
- current accepted Context revision;
- current accepted Question revision;
- latest stable Context frame/image identity;
- latest stable Question frame/image identity;
- pair generation;
- pending pair-change state.

It must not perform OCR, Vision requests, GUI rendering, or network calls.

---

## 13. Pair acceptance semantics

### 13.1 Initial pair

The first analysis is emitted only when both regions have reached a stable accepted state.

```text
Context stable
AND
Question stable
→ Pair Generation 1
```

If Context stabilizes first while Question is still changing, emit nothing.

### 13.2 Question-only change

```text
C1 + Q1
↓
C1 + Q2
```

After Q2 becomes stable:

```text
→ pair_generation += 1
→ analyze C1 + Q2
```

The Context revision is reused.

### 13.3 Context-only change

```text
C1 + Q1
↓
C2 + Q1
```

After C2 becomes stable:

```text
→ pair_generation += 1
→ analyze C2 + Q1
```

A Context change can affect the correct answer even if the visible Question text did not change, so re-analysis is required.

### 13.4 Both regions change

```text
C1 + Q5
↓
C2 + Q1
```

Do not emit a pair as soon as only one side stabilizes.

Required behavior:

```text
C2 stable, Q1 changing
→ no request

C2 stable, Q1 stable
→ exactly one request for C2 + Q1
```

The system must not produce transient combinations such as:

```text
C2 + Q5
```

when the page is clearly transitioning to a new group.

### 13.5 Transient changes

If either region enters CHANGING because of a temporary popup, spinner, loading state, hover, or animation and eventually returns to its existing baseline, no new pair is generated.

## 14. Pair monitor state

The product UI should continue using the existing compact `MonitorState` vocabulary.

Recommended pair-state projection:

```text
STOPPED
    session stopped

PAUSED
    session paused or faulted

ARMING
    either region has not completed initial/re-arm stability

CHANGING
    either region is actively changing

WATCHING
    both regions are armed/stable
```

Do not expose separate Context/Question monitor states in the normal mini controller.

Detailed component states can remain in debug logging and tests.

## 15. Pair snapshot

When the Pair Coordinator accepts a new pair, the analysis layer must receive the full-resolution images corresponding to the accepted pair.

Recommended immutable snapshot:

```python
@dataclass(frozen=True)
class ContextQuestionSnapshot:
    generation: int
    context_revision: int
    question_revision: int
    context_image: QImage
    question_image: QImage
```

Images should be copied/detached when the snapshot is created so later screen ticks cannot mutate the analysis input.

The snapshot is the boundary between monitoring and analysis.

---

## 16. Analysis request model

Keep existing `AnalysisRequest` behavior for Single Region mode.

Add a specific dual-region request type instead of making `AnalysisRequest.image` ambiguous.

Recommended shape:

```python
@dataclass(frozen=True)
class ContextQuestionAnalysisRequest:
    generation: int
    mode: AnalysisMode
    context_image: QImage
    question_image: QImage
    context_revision: int
    question_revision: int
    source: str = "auto_watch_context_question"
    session_id: str = ""
    request_id: str = ""
```

The request must copy both images in `__post_init__`, mirroring current detached-image behavior.

## 17. Dispatcher strategy

Do not implement a second Latest-Wins dispatcher.

The existing `AnalysisDispatcher` already owns the concurrency semantics that v0.8.1 needs:

- one active worker;
- one latest pending request;
- delayed request replacement;
- cancellation;
- generation checking;
- stale result suppression;
- stop semantics;
- observability.

Extend it minimally so it can submit a dual-region request and select the appropriate worker factory.

Possible API:

```python
dispatcher.submit_context_question(
    context_image,
    question_image,
    mode,
    context_revision=...,
    question_revision=...,
    generation=...,
    session_id=...,
)
```

Pair generation remains the dispatcher's generation authority.

Existing Single Region `submit()` behavior must remain unchanged.

## 18. Text / OCR pipeline

Text mode should keep Context and Question semantically separate.

Do not simply concatenate the two images and OCR the composite.

Required flow:

```text
Context image
    ↓
Context OCR
    ↓
context_text

Question image
    ↓
Question OCR
    ↓
question_text

context_text + question_text
    ↓
structured DeepSeek request
```

This preserves the meaning of the two regions and enables Context OCR caching.

---

## 19. Context OCR cache

Context OCR caching is part of v0.8.1, not a later optimization.

Cache key:

```text
context_revision
```

Recommended session-owned cache:

```text
cached_context_revision
cached_context_ocr_result
```

Behavior:

```text
C1 + Q1
→ OCR C1
→ OCR Q1

C1 + Q2
→ reuse OCR C1
→ OCR Q2

C1 + Q3
→ reuse OCR C1
→ OCR Q3

C2 + Q1
→ OCR C2
→ OCR Q1
```

No hash/checksum is needed. The visual monitor has already decided whether the Context revision changed.

The cache is session-only and cleared on Stop/new session.

## 20. Context + Question Text worker

Add a dedicated worker for dual-region Text mode rather than overloading the current `ProcessingWorker` with many optional arguments.

Suggested file:

```text
app/workers/context_question_processing_worker.py
```

Responsibilities:

1. check cancellation;
2. obtain Context OCR from cache or OCR provider;
3. OCR the Question image;
4. emit useful progress signals;
5. call the structured Context + Question DeepSeek API;
6. return a structured result;
7. cooperate with cancellation exactly like the current processing worker.

Suggested result model:

```python
@dataclass(frozen=True)
class ContextQuestionPipelineResult:
    context_ocr: OCRResult
    question_ocr: OCRResult
    answer: str
    context_revision: int
    question_revision: int
```

## 22. Vision pipeline

Do not add multi-image API semantics in v0.8.1.

The existing Vision path expects one `QImage`, encodes it to PNG, and sends one image request.

Add an in-memory composite builder:

```text
app/auto_watch/composite.py
```

Recommended API:

```python
compose_context_question_image(
    context_image: QImage,
    question_image: QImage,
) -> QImage
```

Target layout:

```text
┌───────────────────────────────────┐
│ CONTEXT                           │
├───────────────────────────────────┤
│                                   │
│ context screenshot                │
│                                   │
├───────────────────────────────────┤
│ QUESTION                          │
├───────────────────────────────────┤
│                                   │
│ current question screenshot       │
│                                   │
└───────────────────────────────────┘
```

Requirements:

- generated entirely in memory;
- preserve readable source resolution as far as practical;
- no disk writes;
- include clear visual separation between Context and Question;
- resulting image enters the existing `VisionProcessingWorker` unchanged.

This avoids a second Vision worker or a new multi-image service contract.

## 27. Answer Window placement with two ROIs

The current Single Region placement avoids one ROI.

Add a general placement helper capable of avoiding multiple rectangles, for example:

```python
place_answer_window_avoiding(
    window_rect,
    avoid_rois,
    available_geometry,
    margin,
)
```

Single Region mode should continue to call it with one ROI, either directly or through the current compatibility function.

Dual Region mode passes:

```text
[
    context_global_roi,
    question_global_roi,

```

Do not reduce the two regions to one simple union rectangle. A Context and Question region can be far apart with useful empty space between them.

Candidate placement should minimize overlap with the actual two ROIs while remaining inside the screen's available geometry.

User manual movement during the watch session should retain the current v0.8.0 behavior: once the user moves the Answer Window, do not continuously override that choice unless the window becomes unusable/off-screen.

## 28. Analyze Now semantics

In Context + Question mode, Analyze Now means:

> Accept the current full-resolution Context + Question pair immediately as the latest pair and analyze it.

Required effects:

- increment pair generation;
- accept/update both detector baselines to the current sampled frames;
- reset pair stability state;
- produce one new pair snapshot;
- route the snapshot through normal Latest-Wins dispatch;
- avoid an immediate duplicate automatic trigger for the same pixels.

Analyze Now should not bypass generation/stale-result protection.

---

## 29. Pause / Resume semantics

### Pause

Pause should:

- stop screen polling;
- retain Context baseline;
- retain Question baseline;
- retain Context OCR cache;
- retain current pair generation;
- not automatically cancel an already running analysis solely because the user paused monitoring.

### Resume

Resume should:

- re-arm both region detectors;
- keep existing baselines for novelty comparison;
- require stability before accepting post-resume changes;
- emit no request when both regions are unchanged;
- emit one request when either region changed while paused and the resulting pair becomes stable.

---

## 30. Stop semantics

Stop must remain a full session cleanup operation.

Dual-region Stop should:

- stop polling timer;
- stop both region coordinators / pair coordinator;
- close overlay;
- close mini controller;
- clear pending pair snapshot;
- clear Context OCR cache;
- stop/cancel dispatcher work using existing semantics;
- wait for active analysis cleanup when required;
- release dual-region session references;
- restore the normal controller state;
- not destroy the application-owned shared Local OCR session.

Stop must remain idempotent.

---

## 31. Display configuration and DPI

v0.8.1 inherits the v0.8.0 display rules.

At session creation capture:

- selected `QScreen` identity;
- screen geometry;
- device-pixel ratio.

During monitoring, if the display disappears, geometry changes, or DPR changes in a way that invalidates the mapping, stop polling and surface a watch-session fault rather than continuing with stale ROI coordinates.

Both Context and Question must be validated against the same display snapshot.

Do not add cross-display migration logic.

---

## 32. Permission and capture failures

Screen Recording permission remains a prerequisite on macOS.

Dual-region setup should perform the same permission checks as existing Auto Watch before selection/monitoring.

Runtime capture failures should:

- stop polling;
- put the session in a faulted/paused state;
- leave Stop available;
- not corrupt dispatcher state;
- not destroy the shared OCR session;
- not silently continue with old captured images.

A single OCR/AI analysis error should not terminate monitoring; later stable pairs must still be analyzable, preserving v0.8.0 behavior.

## 35. Phase 1 — Dual Region Core

### Goal

Prove that two ROIs can be sampled efficiently and converted into correct pair generations without involving OCR, AI, or production setup UI.

### Implement

- `ContextQuestionRegions` / region role models;
- same-screen validation;
- `ContextQuestionSampler` using one screen capture per tick;
- `PairCoordinator`;
- pair generation semantics;
- Pause / Resume / Analyze Now core behavior;
- synchronous unit tests.

### Required scenarios

```text
1. Initial C1 + Q1
   → exactly one initial pair

2. C1 + Q1 → C1 + Q2
   → exactly one new pair

3. C1 + Q1 → C2 + Q1
   → exactly one new pair

4. C1 + Q1 → C2 + Q2
   where Context stabilizes first
   → zero request until Q2 stable
   → exactly one request after both stable

5. temporary Context popup → return to C1
   → zero new pair

6. temporary Question popup → return to Q1
   → zero new pair

7. scrolling / continuous instability
   → zero pair while changing

8. Pause → unchanged → Resume
   → zero new pair

9. Pause → Question changes → Resume
   → one pair after stable

10. Analyze Now
    → one immediate pair generation
    → no duplicate automatic generation for same frame
```

### Forbidden in Phase 1

- AI calls;
- OCR calls;
- production Controller dual-region UI;
- Answer Window changes;
- Vision composite;
- context OCR cache;
- packaging/version bump/release work.

---

## 36. Phase 2 — Analysis Pipeline

### Goal

Route accepted pair snapshots through Text/OCR and Vision while preserving v0.8.0 dispatch guarantees.

### Implement

- `ContextQuestionAnalysisRequest`;
- dispatcher dual-region submission path;
- ContextQuestion Text worker;
- Context OCR cache;
- `DeepSeekService.analyze_context_question()`;
- structured Text result;
- Vision composite builder;
- existing Vision worker reuse;
- Latest-Wins tests for pair generations.

### Critical tests

Context OCR caching:

```text
C1 + Q1 → Context OCR called
C1 + Q2 → Context OCR not called again
C1 + Q3 → Context OCR not called again
C2 + Q1 → Context OCR called for C2
```

Latest-Wins:

```text
Pair 10 analysis running
Pair 11 accepted
Pair 12 accepted before 10 finishes

→ obsolete work cancelled where possible
→ Pair 12 becomes latest pending
→ Pair 10 result cannot replace Pair 12
→ Pair 11 must not create a stale queue backlog
```

Vision:

```text
Context + Question
→ one composite QImage
→ existing Vision worker
→ one API request
```

## 41. Performance expectations

v0.8.1 should remain lightweight while idle.

Target characteristics:

- same 250 ms default polling interval as v0.8.0;
- one `grabWindow(0)` per polling tick;
- two small detector preprocess operations per tick;
- no OCR until a stable pair is accepted;
- no repeated Context OCR while the Context revision remains unchanged;
- no disk image persistence;
- no second background polling thread unless profiling proves the GUI-thread timer approach is insufficient.

Do not introduce performance complexity without a measured problem.

## 42. Compatibility and regression boundary

v0.8.1 must preserve these public behaviors:

```text

Manual Vision capture

Single Region Auto Watch Vision
Settings behavior
Local OCR component behavior
Tray behavior

```

The safest implementation strategy is additive:

```text
existing Single Region path
    stays intact

new Context + Question path
    reuses detector/dispatcher primitives
    adds pair-specific orchestration
```

Do not convert all current Single Region code into generic N-region infrastructure. v0.8.1 only needs exactly two roles: Context and Question.

## 43. Frozen decisions

The following decisions are considered settled for implementation unless real testing disproves them:

1. v0.8.1 feature name: Context + Question Auto Watch.
2. Single Region remains the default/compatible mode.
3. Dual Region supports exactly one Context and one Question.
4. Both regions must be on the same display.
5. One full-screen capture is shared by both ROI crops.
6. Existing v0.8.0 detector/stability algorithm is reused.
7. Context and Question have independent revisions.
8. AI uses pair generation, not region generation.
9. A pair is analyzed only when the resulting Context + Question combination is stable.
10. Context-only stable changes trigger re-analysis.
11. Question-only stable changes trigger re-analysis.
12. Context OCR is cached by Context revision.
13. No hashes/checksums are required for Context caching.
14. Text mode OCRs Context and Question separately.
15. Vision mode composes the two images into one in-memory image.
16. Existing Latest-Wins dispatcher semantics are reused, not duplicated.
17. Answer Window avoids two actual ROIs rather than one union rectangle.
18. Pause retains Context cache and baselines.
19. Resume re-arms detectors and does not duplicate unchanged pairs.
20. Analyze Now accepts the current pair and updates both baselines.
21. No ROI persistence or profiles in v0.8.1.
22. No detector sensitivity/SSIM/pHash work unless actual evidence requires it.
23. No browser/mobile work in this release.

## 44. Definition of done

v0.8.1 is ready for release when all of the following are true:

- Context + Question setup is understandable without developer knowledge;
- the two selected ROIs remain on one validated display;
- polling captures the screen only once per tick;
- the initial stable pair is analyzed once;
- Question-only changes produce exactly one new pair analysis;
- Context-only changes produce exactly one new pair analysis;
- simultaneous Context + Question transitions do not emit transient mixed pairs;
- Text mode reuses cached Context OCR while Context is unchanged;
- Vision mode creates one valid composite image per accepted pair;
- Latest-Wins and stale-result rejection remain correct under rapid changes;
- Pause / Resume / Analyze Now / Stop behave consistently with v0.8.0;
- Answer Window avoids both monitored ROIs where practical;
- individual analysis errors do not terminate monitoring;
- all existing Single Region Auto Watch tests remain green;
- manual Text and Vision capture remain unchanged;
- Windows x64, macOS Intel, and macOS ARM64 release builds succeed;
- no unrelated Lite or Local OCR changes are included.

At that point the feature can proceed through `v0.8.1-rc.1` to the final `v0.8.1` release.
